# 视觉版性能验收

本次分别测量地图投影/标记规划、实际画面绘制函数的 CPU 指令提交，以及生产构建的文件大小。三个数字不是同一回事，均不能换算为实体手机帧率。

## 密集地图

复现：`npm run map:benchmark`。同一 Linux 云端环境（Node 24.22.3、AMD EPYC 9V74）连续跑两次；每次固定种子 13071，27 个场景（48/526/1,221 位在册修士，三种视野，360/390/1440px），每场景预热 24 次、计时 120 次。两次的可见成员、标记及命中校验和完全一致；迷雾没有画出未获准的路线。

| 指标 | 最慢场景 | 第一次 P95 | 复测 P95 |
| --- | --- | --- | --- |
| 世界投影 | 1,221 人、360px 全景 | 0.499 ms | 0.827 ms |
| 标记规划 | 同上 | 0.283 ms | 0.458 ms |
| 投影与规划合计 | 同上 | 0.783 ms | 1.230 ms |

该脚本不绘制画布，也不统计浏览器合成、缩放动画或触控响应时间。

## 构建资源

对同版生产视觉构建的每个文件使用 `gzip -n` 单独统计。199 个生成文件原始合计 9,382,472 字节，压缩合计 3,142,355 字节；这包括按需加载的页面和 Worker，**不是**首次下载量。HTML 明确列出 73 个模块预加载；加上入口 JS、HTML、CSS 共 76 个文件，逐文件压缩合计 956,628 字节。不含缓存、协议开销或实际浏览器追加请求。

## 实际画面函数的 CPU 开销

复现：`./node_modules/.bin/vite-node scripts/visualPerformanceAudit.ts`。两次独立运行使用同一原生第 5 月现场；丹霞采药有真实事件，庭院有 5 位在场修士和 4 类设施。四种逻辑宽度为 360、390、1112、1440px，每类画面预热 24 次、计时 120 次。两次非计时指标及确定性绘制校验和一致。表中取每次四种宽度中的最大 P95。

| 实际画面函数 | 第一次 P95 | 复测 P95 | 每帧绘制指令上界 |
| --- | --- | --- | --- |
| 地图地貌冷重建 | 9.096 ms | 9.505 ms | 81,473 |
| 地图当前可见绘制子集，含地标、小人与名牌 | 0.599 ms | 0.758 ms | 5,613 |
| 故事戏台 | 0.767 ms | 0.879 ms | 6,242 |
| 丹霞庭院 | 3.507 ms | 3.874 ms | 34,134 |

本表使用记录 Canvas 指令的接收器，只计量绘制函数的 JS 指令提交及接收器本身的开销，没有栅格化、字体实测、布局或 GPU 合成。地貌重建是冷路径，不能把该数当作每帧地图成本；地图子集也不是整张网页。逻辑尺寸及 DPR 控制可复查，实体手机的帧率与掉帧没有被测量。

## 线上与真机验收边界

线上 v125 的原试玩地址在云端 Chrome 打开后显示 ChatGPT 登录页。该次会话未进入游戏，独立的离线无头浏览器也未能启动。因此这里不把 Canvas 指令测量或逻辑宽度当成实机验证；也未测得线上资源的实际网络传输、浏览器帧率、实体手机触控或键盘焦点回归。测试套件覆盖相关组件与调度逻辑，但登录后的移动浏览器验收仍须单独完成。
